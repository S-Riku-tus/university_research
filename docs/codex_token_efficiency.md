# Cursor内Codexの利用枠を節約する運用

更新日: 2026-09-16。対象は、Cursor上でOpenAI Codex IDE拡張機能を使ってこのリポジトリを扱う場合である。

## Cursorサイドバーを基準にする

モデルとreasoning effortは `.codex/config.toml` に固定せず、CursorのCodexサイドバーで新しいチャットを始める際に選択する。この使い方なら、前回の難問でAstraを使ったことを理由に、別の通常作業までAstraで始めることを避けやすい。

`.codex/config.toml` には、モデル選択と独立して常時役立つ次の2項目だけを置く。

| 項目 | 設定 | ねらい |
|---|---|---|
| verbosity | `low` | 作業能力ではなく説明文の長さを抑える |
| tool output | 6,000 tokens/出力 | 巨大ログが会話履歴を占有するのを抑える |

CodexのCLIとIDE拡張は同じ設定レイヤーを共有する。そのため、モデルをプロジェクト設定に書くと、サイドバー中心の運用に対して不要な既定値が増える。プロジェクト設定は、Cursorでこのフォルダを信頼している場合に読み込まれる。

## モデルを上げる順序

作業内容を事前に完全分類する必要はない。サイドバーで通常モデルから開始し、具体的な不足が出たときだけ一段ずつ上げる。

1. 通常はサイドバーで `GPT-5.6 Sol / medium`を選ぶ。
2. 原因候補が複数残る、設計判断が難しい場合は `Sol / high`。
3. それでも解けない、または重要な最終レビューは `GPT-6 Astra / low`、必要なら `medium`。
4. `Astra / high`や`max`は、上記で不足した難問に短時間だけ使う。

軽い探索、定型編集、要約だけなら、利用可能な場合はTerraへ下げてもよい。モデルを下げて失敗と再試行が増える作業では、既定のSolを使う方が総消費を抑えやすい。

Fast modeは応答時間を縮める代わりに利用枠を速く消費するため、通常は選択しない。この設定ファイルはFastを指定していない。残量はCodexの `/status` または利用状況画面で確認する。

公式の現在の目安では、Plusのローカルメッセージは5時間あたりAstraが5～45、Solが10～100、Terraが25～200で、週次上限も適用される場合がある。ただし固定メッセージ数ではなく、処理量により変わる。残量とリセット時刻は利用状況画面を正とする。

## Cursorでの基本手順

### 1タスク1スレッド

一つのバグ、実験条件、報告書など、同じ目的の調査→変更→確認は同じスレッドで続ける。目的が変わったら新しいスレッドにする。Cursorで開いている大量のファイルやフォルダ全体を習慣的に添付せず、対象ファイル、選択範囲、エラー周辺だけを渡す。

### 難しいモデルへ渡すとき

長い既存スレッドをそのままAstra Maxへ切り替えるより、新しいスレッドへ短い引継ぎを渡す。

```text
目的:
何を成立させたいか。

対象:
- 関連ファイルまたはrun

確認済み:
- 分かった事実
- 実行した最小チェックと結果

未解決:
- 残る仮説または判断点

依頼:
上記だけを前提に、必要なファイルを追加確認して○○をレビューする。
```

研究結果では、データ版、学習/検証/テスト分割、モデル、seed、評価単位、比較対象も引継ぎに含める。会話全文より、固定した `experiments/` の記録を参照させる。

### 探索とテスト

- 「リポジトリ全体を全部読む」ではなく、関連記号・パスを検索してから必要部分を読む。
- 全ログではなく、失敗箇所、末尾、要約、対象epochなどを取得する。
- 対象モジュールのcompile、関連テスト、短いdry-runの順に確認し、必要な根拠がある場合だけ全体へ広げる。
- 大きな `.npy`、全スペクトログラム、学習済み重みを会話へ直接入れず、manifest、集計CSV、代表図、日付付き解析を使う。
- 外部サービスが不要な作業では、使わないMCPサーバー、プラグイン、コネクタを増やさない。利用可能なツールの説明自体も毎回のコンテキストになる。

## 依頼文の最小形

```text
目的: 何を直す／確認するか。
成功条件: 何が成立すれば完了か。
対象: 分かっているファイル、run、エラー。
制約: 変えてはいけない条件や比較基準。
確認: 最小の関連チェックから行い、成功条件を満たしたら終了する。
```

「徹底的に全部」「可能な改善もすべて」など範囲のない依頼は、探索、編集、テスト、出力を増やしやすい。深い調査が必要な場合も、問いと終了条件を先に固定する。

## 設定を変える場合

モデルとreasoningは、そのスレッドの目的に合わせてCursorサイドバーで選ぶ。`.codex/config.toml`へモデルを追加するのは、将来このリポジトリで常に同じ既定を使いたくなった場合だけでよい。6,000 tokensで診断に必要な出力が切れる場合は、まず対象コマンドを狭める。それでも不足する場合だけ `tool_output_token_limit` を増やす。

`model_context_window` と自動compact閾値は、モデル既定に任せる。大きなcontext windowを明示しても、利用枠の節約にはならない。長い作業は、フェーズ終了時に要点を文書へ固定し、新しいスレッドへ引き継ぐ。

Cursor独自Agentも併用する場合だけ `.cursor/rules/` を追加する。Codex拡張向けの共通指示は `AGENTS.md` に一本化し、同じ長文をCursor User Rulesへ重複登録しない。
